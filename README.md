# agents-md

我的全域 `AGENTS.md`：每個專案都會載入的開發守則，給 coding agent（omp、Claude Code、Codex 等）遵循。

本機的 `~/.omp/agent/AGENTS.md` 是指向這個 repo 中 `AGENTS.md` 的 symlink，改規則就直接在這裡 commit。

## 為什麼需要這份守則

Coding agent 預設的傾向通常是「多做一點比較保險」：多寫註解、順手重構、保留舊介面、加 fallback、預先抽象化。單看每一項都合理，累積起來就是難以 review 的大 diff、越來越厚的相容層，以及之後得有人收拾的權宜做法。

這份守則的目標是讓 agent 的產出像一位紀律良好的資深工程師：改動小而完整、程式碼自己說明自己、架構以長期為準，回報時讓人一眼看出做了什麼、驗證到什麼程度。

## 規則與用意

### 1. 註解只解釋「為什麼」

> 「做什麼」用命名、型別、具名函式或常數表達；註解留給程式碼表達不出的原因。

- **用意**：描述「做什麼」的註解會和程式碼重複，而且程式碼改了註解常常沒跟著改，最後變成誤導。把意圖寫進命名與結構，程式碼本身就是唯一的事實來源。
- **保留的空間**：外部限制、規避的 bug、刻意的取捨、看起來不直觀的決定，這些從程式碼讀不出來，正是註解存在的價值。
- **工具指示詞不算註解**：`// @ts-expect-error`、`# type: ignore`、shebang 等是給工具的指令，照常使用。
- **不動既有註解**：別人的註解可能承載你不知道的脈絡。只有在改動範圍內、且註解因這次改動而失效時才更新。

### 2. 最小改動，只處理目前的問題

> 只改必要的行；不重排、不改名、不調整格式、不升級依賴。

- **用意**：diff 越小越好 review、越好 revert、越不容易藏 regression。把格式調整或重構混進功能修改，會讓 reviewer 無法分辨哪些是實質變更。
- **允許的小修正**：一眼能確認、只動幾行、不需要判斷的問題（錯字、未使用的 import、明顯的小 bug）可以順手修。門檻設在「不需要取捨判斷」，因為一旦需要判斷，就應該讓人類決定。
- **連帶修改屬於範圍內**：改了函式簽名，呼叫端、型別、測試就要一起改完。最小改動不是做一半。
- **最小不等於權宜**：如果在範圍內做不出長期解法，就停下來說明選項，而不是塞一個「先頂著」的 hack。

### 3. 不保留向後相容

> 舊路徑或介面過時就直接移除，不加相容層或 fallback。

- **用意**：個人與小團隊專案很少真的有外部消費者需要相容期。相容層會讓程式碼同時存在兩套做法，後來的人（和 agent）不知道該用哪一套，而「暫時保留」的東西幾乎不會被移除。
- **資料例外**：已經存在的資料（資料庫 schema、設定檔、持久化檔案）不能遺失。格式變動時提供一次性轉換，轉換完就刪掉舊格式的讀取路徑，不留雙軌。

### 4. 設計與架構

- **最簡單且完整的實作**：不做推測性的抽象、設定或間接層。「以後可能會用到」的彈性大多用不到，卻每天都要付出理解成本。
- **分層成長**：先做出能端到端運作的最小版本，新能力疊在已經能用的產品上。最小版本是地基，不是之後要丟掉的原型；也不拿能用的東西去換尚未完成的複雜度。
- **模組化、關注點分離**：讓每個元件可以單獨理解與替換。
- **以長期為準**：拒絕「先這樣，之後再換」的做法。這種之後通常不會來，或來的時候代價更高。

### 5. 依賴與函式庫

- **先用既有依賴**：專案已有的工具通常就夠用，新增依賴會增加維護、安全與建置成本。
- **先查文件再下結論**：agent 很容易憑印象認定某個函式庫「沒有這個功能」然後自己重寫。查過文件與型別之前不做這個假設。
- **新增套件要先問**：說明要加什麼、為什麼需要、為什麼既有依賴不夠，由人類決定是否接受這份長期成本。
- **成熟函式庫優先於自幹**：能降低複雜度或提高可靠度時就採用，不要重新發明常見功能。

## 回覆語言與格式

- 回覆使用繁體中文，這是我日常思考與閱讀最快的語言。
- commit message 與 PR 使用英文，配合開源協作慣例與工具生態。
- 程式碼註解用繁體中文；參與別人的專案時跟隨該專案原本的語言，尊重既有慣例。
- 不使用 emoji：在終端機、commit log 與文件中是雜訊，也會降低專業感。

## 回報範圍

> 只回報這次問的東西；順帶看到但沒修的事不寫進回覆，也不另外查證。

- **用意**：回報是用來決策的，不是用來展示 agent 看了多少東西。混入範圍外的發現會稀釋重點，也會引導 agent 花時間去查證與任務無關的事。

## 回報格式

純問答直接回答；完成任務後依序回答四個問題：

1. **完成了嗎？** 開頭就給結論，未完成要說缺什麼。讓人不用讀完全文就知道狀態。
2. **改了什麼？** 每個檔案改了什麼、為什麼改；沒改檔案要明說。這是 review 的索引。
3. **做了哪些驗證？** 列出實際跑過的驗證，以及為什麼足以證明完成；沒驗證到的部分要明說。這一項用來防止「看起來完成」與「確實完成」之間的落差。
4. **順手修了什麼？** 有才列。讓第 2 條允許的小修正保持透明，不會混在主要改動裡被忽略。

## 使用方式

把 `AGENTS.md` 放到你的 agent 會讀取全域指示的位置，例如：

| Agent | 位置 |
| --- | --- |
| omp | `~/.omp/agent/AGENTS.md` |
| Codex | `~/.codex/AGENTS.md` |
| Claude Code | `~/.claude/CLAUDE.md` |

建議用 symlink 指回 clone 下來的 repo，改規則時直接 commit：

```sh
git clone https://github.com/PttCodingMan/agents-md.git ~/agents-md
ln -sf ~/agents-md/AGENTS.md ~/.omp/agent/AGENTS.md
```
